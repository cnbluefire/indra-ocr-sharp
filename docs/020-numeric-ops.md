# 020 — Numeric primitives (numpy parity)

Status: done

## Goal

Provide the shared numeric helpers the rest of the port needs, with semantics matching the
numpy operations the Python pipeline actually uses.

## Deliverables

- `src/Indra.Ocr.Core/Numerics/Numerics.cs` (namespace `Indra.Ocr`, class `Numerics`):
  - Reductions: `Median` (over `float` = float32 reduction like numpy, over `double`),
    `Percentile` (default "linear" interpolation), `Mean`.
  - Ordering: `ArgMax`/`ArgMin`, `ArgSort` (ascending, **stable**), `ArgSortDescending`,
    `ArgSortByKey` (stable, for Python `sorted(key=...)`).
  - `Bincount` (counts → int64, and weighted → float64), mirroring `np.bincount`.
  - `Log1p` (accurate series/Correction; .NET has no `Math.Log1p`) and `LogAddExp`
    (numpy's edge handling: `-inf`, equal-argument `+log 2`, otherwise `log1p(exp(x-y))+y`).
  - `CumSum`, `SearchSorted` (`left`/`right`), and matrix products `MatMul` (float64) /
    `MatMulF` (float32).
- `tests/Indra.Ocr.Tests/NumericsTests.cs` + `fixtures/numerics.json` generated by
  `tools/scripts/test/gen_numerics.py` running the real numpy.

## Parity notes / decisions

- **`np.argsort` ties.** numpy's default quicksort argsort is a CPU-specific SIMD network;
  equal-key order is machine-dependent. This machine has **AVX2** (no AVX512) and numpy
  returns e.g. `[6,1,4,3,2,0,5]` for `[3,1,3,2,1,3,0]`, which the generic introsort does
  not. We use a **stable** argsort instead and record the deviation in `AGENTS.md`. Keys
  that are distinct (the common case) sort identically.
- **Median dtype.** `np.median` on a float32 array reduces in float32; `Numerics.Median`
  over `float` reproduces that (then widens), avoiding ~1e-7 drift.
- `Math.Log1p` does not exist in .NET, so `Numerics.Log1p` uses the Kahan
  correction (`log(u) - ((u-1)-x)/u`) which matches C `log1p` to ~1 ulp.
