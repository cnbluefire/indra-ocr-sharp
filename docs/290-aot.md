# 290 — NativeAOT: the properties, and the two warnings that had to go

## Goal

Make the whole solution AOT-ready:

- every class library — `Indra.Ocr.Core`, `Indra.Ocr`, `Indra.Ocr.Pdf` — sets
  `IsAotCompatible`, so the trim (IL2xxx) and AOT (IL3xxx) analyzers run on every build;
- both hosts — `Indra.Ocr.Cli`, `Indra.Ocr.Viewer` — set `PublishAot`, so `dotnet publish -r
  <rid>` produces one native executable with no runtime to install;
- and the warnings that came with that are fixed or, where they cannot be fixed, suppressed
  with a reason: `IL3000` in the worker pool and ImageSharp's `IL2104`/`IL3053`.

A plain `dotnet build` (and therefore the tests and every harness, which run
`bin\Debug\net10.0`) is unchanged: `PublishAot` only takes effect on `publish`, and the
analyzers are the only build-time addition.

## The properties

| project | property |
|---|---|
| `Indra.Ocr.Core`, `Indra.Ocr`, `Indra.Ocr.Pdf` | `<IsAotCompatible>true</IsAotCompatible>` |
| `Indra.Ocr.Cli`, `Indra.Ocr.Viewer` | `<PublishAot>true</PublishAot>` |

`PublishAot` implies `IsAotCompatible` (and `PublishTrimmed`, and a self-contained publish with
a RID), so the hosts need nothing else. The test project is neither: it is never published, and
its own analyzers would only add noise.

`src/Directory.Build.props` gains one more `NoWarn`, next to the advisories already there:

```xml
<NoWarn>$(NoWarn);IL2104;IL3053</NoWarn>
```

## `IL3000` — `Assembly.Location` in the worker pool

`WorkerPool.WorkerStartInfo` starts a worker by running *this same program* again, and when the
program is running under a `dotnet` host (`dotnet indra-ocr.dll`) the host needs the assembly as
its first argument. It asked for the path with `Assembly.GetEntryAssembly()?.Location`, which
the trimmer flags:

```
warning IL3000: 'System.Reflection.Assembly.Location.get' always returns an empty string for
assemblies embedded in a single-file app.
```

It is now built from the two things that are always true instead:

```csharp
string name = typeof(WorkerPool).Assembly.GetName().Name!;
info.ArgumentList.Add(Path.Combine(AppContext.BaseDirectory, name + ".dll"));
```

`AppContext.BaseDirectory` is the directory the app was loaded from (not the current
directory), and a framework-dependent app's entry assembly is `<assembly name>.dll` in it — the
check a few lines above has already proved this assembly *is* the entry assembly. A `dotnet`
host is also the one case a single-file or NativeAOT build cannot be in: such a build is its own
host, so the branch is not taken and there is no assembly path to want.

Probe (`temp/probe`, then deleted) for the record: under `dotnet probe.dll`,
`Environment.ProcessPath` is `dotnet.exe`, `Environment.GetCommandLineArgs()[0]`,
`AppContext.BaseDirectory + "probe.dll"` and `Assembly.GetEntryAssembly().Location` are all the
same path, and the file exists; under the apphost the same three agree while `ProcessPath` is
`probe.exe`.

The pool's behaviour is untouched, and the worker path is covered by the harness's pool cases —
including against the trimmed publish below, where the worker really is a self-contained binary.

## ImageSharp's `IL2104` / `IL3053`

`SixLabors.ImageSharp` 2.1.13 — the last Apache-2.0 release, chosen deliberately (3.x/4.x are
under the Six Labors Split License and 4.x refuses Release builds without a key, see
`Directory.Packages.props`) — predates the trim/AOT annotations, so the trimmer reports it as an
assembly that produced warnings:

```
SixLabors.ImageSharp.dll : warning IL2104: Assembly 'SixLabors.ImageSharp' produced trim warnings.
SixLabors.ImageSharp.dll : warning IL3053: Assembly 'SixLabors.ImageSharp' produced AOT analysis warnings.
```

What is actually behind them was checked with `-p:TrimmerSingleWarn=false`, which turns the
per-assembly summaries back into the individual warnings: the whole set is **one** warning,

```
IL2075: SixLabors.ImageSharp.Metadata.Profiles.Exif.ExifTagDescriptionAttribute.GetDescription(
        ExifTag, Object): 'this' argument does not satisfy 'DynamicallyAccessedMemberTypes.PublicFields',
        'DynamicallyAccessedMemberTypes.NonPublicFields' in call to 'TypeInfo.GetDeclaredField(String)'.
```

i.e. reflection over the fields of an EXIF tag to print a tag's description. The port decodes
pixels and reads no metadata at all: it never reaches that method, and the rest of the codec
(ImageSharp's PNG/JPEG decoders, the pixel buffers, `Rgba32`) is pure managed code with no
reflection. Upgrading is the only real fix and it is ruled out by the licence, so the two
summaries are suppressed — with the comment in `Directory.Build.props` saying exactly this, and
saying how to see the individual warnings again (`-p:TrimmerSingleWarn=false`), because the
summaries would otherwise hide a *new* package's warnings too.

## What could be verified here, and what could not

This machine has no MSVC toolchain (no Visual Studio, no Windows SDK, no `link.exe`), so the
AOT publish stops at its first step:

```
error : Platform linker not found. Ensure you have all the required prerequisites documented at
https://aka.ms/nativeaot-prerequisites ...
```

That is a *platform* prerequisite, not a code problem — and the half of the AOT pipeline that
can be run without it is the half that matters for a warning like ImageSharp's: **trimming**.

`PublishAot=false -p:PublishTrimmed=true -p:SelfContained=true` runs ILLink (the same analysis
the AOT publish runs before ILC) and produces a runnable self-contained app. Both hosts were
published that way:

- **0 warnings** from either publish (the ImageSharp summary is suppressed, nothing else
  appeared: not from the pipeline, not from ONNX Runtime, not from PDFium, not from Kestrel or
  the minimal API);
- the trimmed **CLI** passes `cli_parity.py` **83/83** and `parity_sweep.py` **24/24** against
  the reference — images through trimmed ImageSharp, PDFs through PDFium, the worker pool (the
  workers being the trimmed binary itself), `--out`, `--math`, the error paths;
- the trimmed **viewer** passes `viewer_cli_parity.py` **20/20** and `viewer_parity.py`
  **12 cases plus `stderr`** — Kestrel, the minimal API, the source-generated JSON, the page
  and the concurrent requests.

So trimming does not change a byte of behaviour. What is left unverified here is ILC's native
code generation, which only needs the toolchain:

```powershell
dotnet publish src\Indra.Ocr.Cli\Indra.Ocr.Cli.csproj    -c Release -r win-x64 -o temp\pub-aot
dotnet publish src\Indra.Ocr.Viewer\Indra.Ocr.Viewer.csproj -c Release -r win-x64 -o temp\pub-aot-viewer
```

(`-r linux-x64` with clang elsewhere.) Expect 0 warnings, then the same four harnesses, pointed
at the published binaries with the two environment variables added for exactly this:

```powershell
$env:INDRA_OCR_EXE = (Resolve-Path temp\pub-aot\indra-ocr.exe).Path
$env:INDRA_OCR_VIEWER_EXE = (Resolve-Path temp\pub-aot-viewer\indra-ocr-viewer.exe).Path
tools\pyenv\Scripts\python.exe tools\scripts\test\cli_parity.py       # 83
tools\pyenv\Scripts\python.exe tools\scripts\test\parity_sweep.py     # 24
tools\pyenv\Scripts\python.exe tools\scripts\test\viewer_cli_parity.py # 20
tools\pyenv\Scripts\python.exe tools\scripts\test\viewer_parity.py    # 12 + stderr
```

The native binary is also worth a smoke run of its own, since it is the only place the runtime
is the compiler's output rather than the installed one:

```powershell
temp\pub-aot\indra-ocr.exe --version
temp\pub-aot\indra-ocr.exe temp\inputs\latin.png --model-dir resources\models
```

## Notes

- **Globalization** is left on (the default). NativeAOT supports it, but on Linux the binary
  then needs ICU at run time; `-p:InvariantGlobalization=true` would remove that dependency.
  It is not set here because it is a behaviour knob — the port's culture-sensitive calls are
  hand-written to match Python, and turning it on is a change to verify, not a packaging
  detail.
- **The viewer's `PublishAot` is honest about what the viewer already was**: source-generated
  JSON (`ViewerJson`) and the minimal API's own request-delegate generator, so nothing in it
  needs run-time code generation. The trimmed publish above is the evidence.
- The `IL3000` fix also removed the last `Assembly.GetEntryAssembly()` from that method: the
  entry-assembly identity it needs is the one the guard already checked.
